# PEAK Calculator — Sector-aware Scope 2 & ECM upgrade

## Context

The current engine (`src/lib/calc/engine.ts` for SME, `src/lib/calc/mncEngine.ts` for MNC) treats every business the same shape: one fixed Singapore grid emission factor (GEF = 0.402 kg CO2/kWh), one blended calibration-curve savings % (8–28%) regardless of *what* in the building actually uses the energy, and electricity priced as a single flat tariff with no distinction between clean and dirty sourcing. The Product Brief (`PEAK_Calculator_Product_Brief_and_Validation_Report.docx`) itself flags several of the gaps this closes: MNC sites outside Singapore currently get Singapore's GEF applied everywhere (§4.2, "materially wrong"), and market-based vs. location-based Scope 2 exists for MNC only, not SME (§2.2).

The user wants four things, confirmed via clarifying questions:
1. **Scope 2 grid emission factor (GEF)** should be user-enterable *inside* the Scope 2 section, not in a separate "Sensitivity / overrides" block — and more generally, all the optional overrides currently dumped into one "Sensitivity — What If?" card (`InputForm.tsx` step 3) should live next to the scope section they actually affect.
2. **Sector-specific energy profiles** (e.g. F&B is refrigeration/cooking-heavy, hospitals are HVAC/hot-water-heavy) should show as a "where your energy goes" chart per sector, with the split editable by the user.
3. **Clean vs. dirty energy price segregation**: split the electricity bill into a renewable-sourced portion (priced at a real Singapore green-tariff premium) and a grid/"dirty" portion, showing both the $ split and the emissions difference.
4. **ECM (Energy Conservation Measures)**: replace the single blended savings-% with a sector-aware catalog of concrete measures (each with its own sourced savings range and cost tier) that the user can select, summing to a bottom-up savings estimate.

Researched, sourced end-use splits (used for item 2/4's defaults) and Singapore green-tariff premium data (item 3) were gathered this session — see "Sourcing" below. Everything added must carry a `source` field and be flagged as a proxy where it is one, per this project's existing convention (every number in `data/*.json` already does this).

## Sourcing gathered this session

- **F&B/restaurant**: cooking ~40–45%, HVAC ~28–40%, refrigeration ~10–25% (higher within kitchen-only slice), lighting ~13%. ([EIA](https://www.eia.gov/todayinenergy/detail.php?id=60241), [ENERGY STAR](https://www.energystar.gov/buildings/resources-audience/small-biz/restaurants))
- **Hospitality**: HVAC ~40–50%, lighting ~15–20%, hot water ~10–15%, laundry ~5–10%, kitchen ~5–10%. ([ACEEE](https://www.aceee.org/files/proceedings/2010/data/papers/1984.pdf), [EIA lodging](https://www.eia.gov/consumption/commercial/pba/lodging.php))
- **Retail (supermarket/grocery)**: refrigeration ~29–40% (up to 60% in small-format), lighting ~17–25%, HVAC ~5–8%. General-merchandise retail does *not* fit this split — flagged as a caveat, user can toggle. ([ScienceDirect](https://www.sciencedirect.com/science/article/pii/S2352484725001052), [EnergySense](https://energysense.uillinois.edu/supermarkets/))
- **Manufacturing**: process heating ~60% (US DOE MECS), remainder split across motors/compressed air/HVAC/lighting. ([energy.gov](https://www.energy.gov/documents/energyuseandlossandemissionsintropdf))
- **Office**: HVAC/cooling + lighting ~⅔ of load, plug loads >20% and the fastest-growing category. ([EIA CBECS](https://www.eia.gov/energyexplained/use-of-energy/commercial-buildings.php))
- **Healthcare**: HVAC/heating ~40–50% (up to 65% in some studies), lighting ~30–40%, ventilation ~15%. ([R-Zero](https://rzero.com/blog/understanding-hospital-energy-usage/), [EIA large hospital](https://www.eia.gov/consumption/commercial/reports/2007/large-hospital.php))
- **Data Centre**: cooling dominant alongside IT load, UPS ~10% of total. ([Huawei](https://digitalpower.huawei.com/en/blogs/data-center-power-usage), [Eaton](https://www.eaton.com/us/en-us/markets/data-centers/data-center-cooling/efficiency/energy-consumption-in-data-centers-air-versus-liquid-cooling.html))
- **Logistics — cold storage**: refrigeration ~70–80%, lighting ~10%. **Logistics — standard/ambient warehouse**: lighting + material handling dominant, refrigeration ~0. Needs a toggle. ([PatSnap](https://www.patsnap.com/resources/blog/articles/cold-storage-energy-tech-cuts-use-30-72-by-2026/))
- **Singapore green electricity premium**: full green (REC-backed) retail plans run **0.5–1.5 ¢/kWh** above standard plans; a REC-only add-on to an existing plan starts from **0.25 ¢/kWh**. ([SingSaver](https://www.singsaver.com.sg/credit-card/blog/open-electricity-market-oem-singapore), [Sunollo](https://www.sunollo.com/blog/singapore-electricity-price-tracker), [MissLobang](https://www.misslobang.com/article/best-electricity-price-plans-singapore-2026))

All of the above are **international/market-survey proxies, not Singapore-regulator-published figures** (unlike GEF or the carbon tax schedule) — every new data file must say so explicitly and the tool must surface it as a warning wherever it's used, matching how `data/scope3_factors.json` already flags its proxies.

## Recommended approach

### 1. Data files (new/extended, `data/`)

- **`data/sector_energy_enduse.json`** (new) — per sector, a list of `{id, label, pct}` end-uses summing to 100, plus `source`/`proxy: true`. Sectors with a bimodal profile (`Retail`, `Logistics`) get two named variants (e.g. `Retail.default` vs `Retail.supermarket`, `Logistics.default` vs `Logistics.coldStorage`) selected by a new boolean input (see §3 below). `Other` gets no split (chart hidden, same pattern as `hasComparableBenchmark` in `benchmark.ts`).
- **`data/ecm_catalog.json`** (new) — flat list of measures: `{id, label, endUseId, sectorTags: string[], savingRange: {low, high} (as % of that end-use's kWh, not total), costTier: "low"|"medium"|"high", evidence, schneiderProductId?}`. `endUseId` links to the sector_energy_enduse category ids so the UI can rank/filter measures by the sector's dominant end-use (the F&B example the user gave: refrigeration/cooling measures surface first). Reuse well-documented DOE/ENERGY STAR ranges for standard measures (LED retrofit, VSD/HVAC, refrigeration door strips, compressed-air leak repair, heat recovery) — cite each.
- **`data/tariff_config.json`** (extend) — add a `greenPremium: { recOnlySgdPerKwh: 0.0025, fullGreenPlanLowSgdPerKwh: 0.005, fullGreenPlanHighSgdPerKwh: 0.015, typicalSgdPerKwh: 0.01, source, proxy: true }` block.

### 2. Types (`src/lib/types/inputs.ts`, `src/lib/types/mncInputs.ts`, `src/lib/types/results.ts`)

All new *optional* overrides go into the scope block they affect, not a separate sensitivity object — this directly satisfies the "no separate section" feedback:

- `BlockAEnergy` (SME, Scope 2/Scope 1-gas block) gains: `tariffOverrideSgdPerKwh?`, `gridEmissionFactorOverrideKgPerKwh?`, `tariffEscalationPctPerYear` (moved from `SensitivitySettings`), `renewableCoveragePct?` (new — clean/dirty split, distinct from `hasSolar` which nets physical generation), `greenTariffPremiumOverrideSgdPerKwh?`.
- `MncSite` (already per-site scoped, good existing pattern) gains: `gridEmissionFactorOverrideKgPerKwh?`, `greenTariffPremiumOverrideSgdPerKwh?`. The existing `sensitivity.tariffOverrideSgdPerKwh` is redundant *as a final override on top of the weighted result*, but a portfolio-wide fallback is still genuinely useful for an MNC with many sites on the same contract rate who shouldn't have to type it per-site. Replace it with clearer semantics at the `MncInputs` top level: `defaultTariffOverrideSgdPerKwh?` and `defaultGridEmissionFactorOverrideKgPerKwh?`, used as `s.tariffSgdPerKwh ?? inputs.defaultTariffOverrideSgdPerKwh ?? DEFAULT_TARIFF` (and the GEF equivalent) — a per-site value always wins, the portfolio default fills gaps, the data-file reference is the final fallback.
- `SensitivitySettings` shrinks to just `savingsRateOverridePct?` — kept as the power-user escape hatch, now positioned next to the new ECM section (§4) instead of a standalone card, since it's "the manual number if you don't want to use the ECM catalog."
- `BlockEBaselineGoals` (SME) and `MncBaseline` (MNC) both gain `plannedEcmIds: string[]` — mirrors the existing `existingSolutionIds` pattern in `src/lib/existingMeasures.ts`.
- New sub-profile field: `BlockAEnergy.subProfile?: string` (SME) / `MncSite.subProfile?: string` (MNC, per-site — cold storage is usually facility-specific) — a string id, not a boolean, that indexes directly into the matching key in `sector_energy_enduse.json` (e.g. `"supermarket"`, `"coldStorage"`). A string union keyed off each sector's available variants scales cleanly as more sub-profiles get added later, instead of accumulating one boolean per sub-profile.
- `results.ts`: add `energyEndUseBreakdown: {id, label, pct, userAdjusted: boolean}[]`, `energyCostBreakdown: {dirtyKwh, cleanKwh, dirtyPaymentSgd, cleanPaymentSgd, greenPremiumPaidSgd, scope2MarketBasedTCo2e, scope2LocationBasedTCo2e}`, and `ecmBreakdown: {ecmId, label, endUseId, kwhSaved, contributionToRatePct}[] | null` to `CalculationResult`. `ecmBreakdown`'s parent result also carries `ecmRatePctLow`/`ecmRatePctHigh` (see §3 below) so the UI can show a sourced range, not just a midpoint.

### 3. Engine changes (`engine.ts`, `mncEngine.ts`)

- **GEF**: `const gef = inputs.energy.gridEmissionFactorOverrideKgPerKwh ?? GEF_BASE;` (SME) — used everywhere `GEF_BASE` currently is, including the 10-year decline projection (decline still applies on top of the override — it represents the *grid* decarbonizing further, which still applies even if the user's own factor differs from the SG default; floor stays 0.1). MNC: per-site `s.gridEmissionFactorOverrideKgPerKwh ?? GEF_BASE`, summed per-site rather than one weighted average (fixes the "Singapore GEF applied everywhere" gap from Brief §4.2 for any MNC site the user knows a different country factor for, without yet building the full ASEAN table).
- **Clean/dirty split**: for SME, add `renewableCoveragePct` handling parallel to what MNC already does (`mncEngine.ts` lines 37–44) — `dirtyKwh = netKwh * (1 - pct/100)`, `cleanKwh = netKwh * (pct/100)`. Market-based emissions (used for the $ savings math, consistent with existing MNC treatment) zero the clean share; also compute and expose location-based emissions (physical, ignores renewable claims) for the new `energyCostBreakdown.scope2LocationBasedTCo2e` — this is the "market-based vs location-based Scope 2" feature the Brief lists as MNC-only (§2.2), now simplified into SME too.
- **Cost split**: `dirtyPaymentSgd = dirtyKwh * tariff`, `cleanPaymentSgd = cleanKwh * (tariff + greenPremium)`, `greenPremiumPaidSgd = cleanKwh * greenPremium`, where `greenPremium = inputs.energy.greenTariffPremiumOverrideSgdPerKwh ?? tariffConfig.greenPremium.typicalSgdPerKwh`. Total electricity cost becomes `dirtyPaymentSgd + cleanPaymentSgd` (replaces the flat `netKwh * tariff` used today) everywhere that figure feeds `currentAnnualCarbonCostSgd` / KPIs. UI copy/tooltip on `renewableCoveragePct` must say explicitly that this assumes the coverage is backed by RECs, a PPA, or a green tariff — i.e. a market-based accounting claim, not a change in physically delivered electricity — which is what justifies both the emissions credit and the premium.
- **New module `src/lib/calc/ecm.ts`**: `computeEcmSavingsRate(sector, endUseBreakdown, selectedEcmIds, subProfile) → { ratePctLow, ratePctMid, ratePctHigh, breakdown }`. End-use `pct` inputs are normalized to sum to exactly 100 before use (if the user's custom split sums to 85 or 115, divide each by that sum) so sloppy input never skews the weighting. Within an end-use, combine selected measures multiplicatively — separately for the catalog's `low` and `high` bounds (`1 - Π(1 - saving_i)`) — so stacked measures don't exceed 100% of that end-use *and* the tool keeps a real low/high range instead of collapsing to one midpoint; across end-uses, weight each end-use's fractional reduction by its normalized `pct` share of total electricity to get a blended whole-building low/mid/high rate. Filter the catalog by `sectorTags` and rank by the sector's largest end-use first (satisfies "F&B sees refrigeration before generic BMS").
- **Priority for `savingRatePct`** in both engines: `sensitivity.savingsRateOverridePct ?? ecmResult?.ratePctMid ?? calibrationCurveRate`. When `plannedEcmIds` is empty (the default, and true for all 6 existing Validation Report scenarios), behavior is unchanged — this keeps the existing validated scenarios backward-compatible.
- **Confidence interval when ECMs are selected**: today `confidence.ts` derives a single `±rangeWidthPct` purely from data-quality tier (`scoreConfidence`/`scoreMncConfidence`) and applies it uniformly to the year-1/10-year totals. When `ecmResult` is present, additionally compute the range implied by `ecmResult.ratePctLow`/`ratePctHigh` around `ratePctMid` and use whichever range is *narrower* — naming specific sourced measures should tighten the illustration's confidence band, not just its headline number, which is also a good "why should I trust this" talking point for the sales conversation the Brief describes.

### 4. UI (`InputForm.tsx`, `MncInputForm.tsx`, new `EnergyEndUseChart.tsx`, `ResultsPanel.tsx`)

- Delete the standalone "Sensitivity — What If?" `SectionCard` (`InputForm.tsx` lines 521–556). Move its three fields: tariff override + new GEF override + tariff escalation into the existing "Scope 2 — Electricity" card (step 1); `savingsRateOverridePct` moves down next to the new ECM picker (see below).
- "Scope 2 — Electricity" card also gains: renewable coverage % slider (with the REC/PPA/green-tariff tooltip above), green-tariff premium field (defaulted, overridable), and — for Retail/Logistics sectors only — a `subProfile` dropdown (e.g. "General retail" vs "Supermarket/grocery") that switches which end-use split is used.
- New **"Where your energy goes"** panel (reuse the `CalibrationCurveChart` visual pattern from `CalibrationCurve.tsx` — a labeled horizontal bar breakdown is simplest) showing the sector default end-use split, with a "customize this breakdown" toggle that turns the bars into editable % inputs (validated to ~100%, matching the `checkIntensityAnomaly` style of soft-warn-don't-block validation already used in `benchmark.ts`).
- New **"Energy Conservation Measures"** section in the Goals & Investment step: checklist of catalog measures for the user's sector (ranked by dominant end-use), each showing its sourced saving range and cost tier; selecting any measure switches the modeled saving rate to the ECM-derived one (shown live, same KPI strip pattern as `LiveKpiStrip.tsx`); the manual override field sits directly below it as the escape hatch.
- `ResultsPanel.tsx` gains a "Clean vs. dirty energy spend" card (dirty/clean $ split, green premium paid, market- vs. location-based tCO2e) and an "How we got to X%" ECM breakdown table when `ecmBreakdown` is non-null.
- `stepFieldGuides.ts`: update field help text for every relocated/new field; remove the "Sensitivity" step entries, add entries under the sections they moved into.
- `src/lib/defaultInputs.ts` / `defaultMncInputs.ts`: add the new fields with neutral defaults (`renewableCoveragePct: 0`, `plannedEcmIds: []`, no GEF/premium overrides) so nothing changes for a user who doesn't touch them.
- `narrative.ts` / `mncNarrative.ts` and `assumptions.ts` / `mncAssumptions.ts`: add lines for the new GEF-override/green-premium/ECM provenance so the plain-English summary and "Illustration basis" stay consistent with what changed, following the existing pattern (e.g. `assumptions.ts` lines 20–70).

### Sequencing

1. Data files + type changes (compiles, no behavior change yet).
2. Engine: GEF override + clean/dirty split + cost split (SME then MNC) — verify against the 6 Validation Report scenarios with new fields left at defaults; numbers should match the existing report exactly since new fields default to no-op.
3. `ecm.ts` + engine wiring for the ECM-driven rate.
4. UI: relocate overrides into Scope 2, add end-use chart, add ECM picker, add results cards.
5. Update guides/narrative/assumptions text; update `defaultSmeInputs`/`defaultMncInputs`.
